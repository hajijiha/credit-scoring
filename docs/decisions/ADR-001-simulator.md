# ADR-001. 대안 데이터 시뮬레이터 설계

| 버전 | 날짜 | 변경 내용 |
|---|---|---|
| v1 | 2026-09-08 | 최초 작성. 대안 5변수를 target·소득·연령 + **개별 노이즈**로 생성 |
| **v2 (현행)** | 2026-09-08 | **공유 잠재요인(성실성) 구조 도입**, 생성 목표 상관을 0.31~0.35 로 하향 |

## 결정 (v2)

GMSC 원본에 대안 데이터 5개 변수를 합성해 붙인다.

- `telecom_payment_rate`, `utility_payment_rate`, `spending_consistency`,
  `regular_payment_count`, `app_login_frequency`

각 변수는 세 성분으로 구성한다.

```
v_i = rho_i * t_z  +  sqrt(1 - rho_i^2) * m_i
m_i = w * shared  +  sqrt(1 - w^2) * eps_i        (t_z 에 직교화 후 표준화)
shared = standardize(0.6 * nuisance + 0.8 * common_noise)
nuisance = 0.7 * z(log1p(MonthlyIncome)) + 0.3 * z(age)
```

- `shared` 는 다섯 변수가 **공유하는 '금융 성실성' 잠재요인**이다. 소득·연령 신호와 공통 노이즈로 만든다.
- `w` = `config.simulator.latent_factor_strength` (현행 값은 아래 "보정 결과" 참조).
- `rho_i` 는 `config.simulator.generation_correlation`(0.31~0.35) 범위에 균등 배치하며,
  변환(정규 CDF·반올림) 후의 실제 상관이 목표에 맞도록 고정점 반복으로 보정한다.
- 검증 기준은 SPEC §4 의 `config.simulator.target_correlation`(0.30~0.50) 범위다.

씬파일러 처리는 [ADR-010](ADR-010-thin-filer-types.md) 에서 유형을 나눈다.
공통으로 `RevolvingUtilizationOfUnsecuredLines`, `NumberOfOpenCreditLinesAndLoans` 에
강한 노이즈를 주입한다.

## 근거

### 씬파일러의 전통 피처 정보량을 줄이는 이유 (v1 부터 유지)

씬파일러의 전통 피처 정보량을 실제로 줄여놓지 않으면, 대안 데이터를 추가했을 때 나오는 성능 향상이
"대안 데이터의 기여"인지 "같은 정보를 두 번 넣은 누수"인지 구분할 수 없다.

### 공유 잠재요인을 도입한 이유 (v2) — v1 의 결합 누수

v1 은 각 변수의 비(非)타겟 성분을 **서로 독립인 개별 노이즈**로 채웠다. 그 결과 타겟을 조건으로 하면
다섯 변수가 거의 독립이 되어(클래스 내부 평균 상관 0.14~0.19) 정보가 그대로 합산됐다.

측정된 결과(스모크, LightGBM/XGBoost, test set):

| 피처 그룹 | v1 test AUC |
|---|---|
| traditional_only | 0.834 |
| alternative_only | **0.996** |
| combined | **0.9999** |

원인 진단:

- 부도율 6.68% 인 이진 타겟에 대해 점이연상관 0.3~0.5 는 매우 강한 조건이다.
  **단일 피처만으로** `|corr|=0.30` → AUC 0.813, `|corr|=0.49` → **AUC 0.944** 가 나온다.
  대안 변수 하나가 전통 모델 전체(0.834)를 이긴다.
- 피처별 집단 분리 효과크기는 Cohen's d = 1.27 ~ 2.22 였고, 조건부 독립 가정 하 결합
  **d = sqrt(Σ d²) = 3.96 → 이론 AUC 0.9975** (관측 0.9959). 관측과 이론이 일치한다.

즉 v1 의 수치는 구현 버그가 아니라 "조건부 독립"이라는 비현실적 가정의 산물이다.
현실에서는 **성실한 사람은 통신비도 공과금도 잘 낸다.** 이 공통 요인을 명시적으로 넣으면
스펙의 상관 요건(0.3~0.5)을 지키면서도 결합 정보량이 현실적인 수준에 머문다.

### 보정 결과

100,000행 시뮬레이션으로 비교한 5변수 결합 AUC:

| 안 | 개별 \|corr\| | 결합 AUC | 스펙 문구 |
|---|---|---|---|
| A. v1 유지 | 0.30~0.49 | 0.998 | 충족 |
| B1. 범위 하단만 사용 | 0.30~0.35 | 0.985 | 충족 |
| **B2. 범위 하단 + 공유 잠재요인 (채택)** | 0.31~0.35 | 0.87 | 충족 |
| C2. 상관 0.15~0.25 + 공유요인 | 0.15~0.25 | 0.789 | **위반** |

목표 구간은 처음에 `combined` test AUC 0.85~0.90 으로 잡았으나,
아래 실측에 따라 **0.90 ~ 0.95 로 정정한다**(사유는 "목표 구간 정정" 절 참조).

### 보정 실측 (GMSC 149,999행, LightGBM class_weight, train fit → test 평가)

**1) `latent_factor_strength` 조정** (생성 상관 0.31~0.35 고정)

| w | 클래스 내부 평균 상관 | traditional | alternative | combined |
|---:|---:|---:|---:|---:|
| 0.85 | 0.692 | 0.8338 | 0.8963 | **0.9470** |
| 0.90 | 0.782 | 0.8338 | 0.8870 | 0.9420 |
| 0.92 | 0.821 | 0.8338 | 0.8843 | 0.9412 |
| 0.94 | 0.861 | 0.8338 | 0.8798 | 0.9396 |

공유 요인을 아무리 키워도 `combined` 는 0.94 아래로 내려가지 않는다.
v1 의 누수(0.9999)는 사라졌지만, 남은 값은 **누수가 아니라 두 정보원의 정상적인 상보성**이다.
전통 모델 0.834 와 대안 모델 0.88~0.90 이 서로 다른 정보를 담고 있으므로 결합하면 0.94 가 된다.

**2) 생성 상관 하한 조정** (w = 0.85 고정)

| 생성 상관 | 실제 \|corr\| | traditional | alternative | combined | SPEC §4 (0.3~0.5) |
|---|---|---:|---:|---:|---|
| 0.31~0.35 | 0.309~0.346 | 0.8338 | 0.8963 | 0.9470 | 충족 |
| 0.26~0.30 | 0.260~0.297 | 0.8338 | 0.8453 | 0.9206 | 위반 |
| 0.22~0.26 | 0.220~0.259 | 0.8338 | 0.7980 | 0.8985 | 위반 |
| 0.18~0.22 | 0.181~0.219 | 0.8338 | 0.7549 | 0.8788 | 위반 |

**결론:** `combined` 를 0.85~0.90 구간에 넣으려면 개별 상관을 0.22~0.26 까지 낮춰야 하고,
이는 SPEC §4 의 "상관계수 0.3 ~ 0.5" 요건 위반이다.
스펙을 지키는 한 `combined` 의 하한은 약 0.94 다.

### 목표 구간 정정: 0.85~0.90 → **0.90~0.95**

`latent_factor_strength` 를 0.85 에서 0.94 까지 올려도 `combined` 는 0.9470 → 0.9396 으로
거의 움직이지 않는다(위 실험표 1). 공유 요인을 키우면 대안 변수들 **사이의** 중복만 늘어날 뿐,
전통 피처와 대안 피처 **사이의** 상보성은 줄지 않기 때문이다.

즉 v2 에서 남은 0.94 는 **누수가 아니라 전통 정보와 대안 정보의 상보성**이며,
이는 이 프로젝트가 증명하려는 현상 그 자체다(씬파일러의 전통 피처 정보량이 낮을수록
대안 데이터가 더 크게 기여한다 — ADR-001 의 설계 목적).

SPEC §4 의 상관 요건(0.3~0.5)을 지키는 한 `combined` 의 하한이 약 0.94 라는 것은
튜닝으로 해소할 수 있는 문제가 아니라 **시뮬레이터의 구조적 성질**이다(위 실험표 2).
따라서 목표 구간을 **0.90 ~ 0.95** 로 정정하고, 현행 설정을 최종 채택한다.

**최종 채택값:** `latent_factor_strength = 0.85`, `generation_correlation = 0.31 ~ 0.35`.

## 한계 (리포트에 명시할 것)

**시뮬레이션 데이터의 한계.** 실제 신용평가 모델의 AUC 는 통상 0.85 ~ 0.88 수준이다.
본 프로젝트의 `combined` AUC 0.94 대는 실제 대안 데이터의 예측력을 나타내는 값이 아니라,
SPEC §4 가 요구하는 "대안 변수와 타겟의 상관계수 0.3 ~ 0.5" 를 부도율 6.68% 인 이진 타겟에
그대로 적용했을 때 발생하는 **시뮬레이터 구조에 기인한 상한**이다.

근거: 점이연상관 `|corr| = 0.30` 은 이 부도율에서 Cohen's d ≈ 1.26 에 해당하고
단일 변수만으로 AUC 0.81 을 준다. 실제 신용 데이터의 개별 변수는 이보다 훨씬 약하다.

따라서 본 리포트의 절대 AUC 수치는 실무 성능의 추정치로 해석해서는 안 되며,
**피처 그룹 간 상대 비교**(전통 vs 대안 vs 통합)와 **집단 간 상대 비교**(씬파일러 vs 일반)에만
의미를 두어야 한다.

## 버린 대안

- **v1 구조 유지(A)**: `combined` AUC 0.9999 는 신용평가 모델로 방어가 불가능하다.
  씬파일러 uplift 도 +0.238 로 비현실적이다.
- **개별 상관만 하단으로(B1)**: 결합 AUC 0.985 로 여전히 과하다. 근본 원인(조건부 독립)이 남는다.
- **상관 요건 자체를 낮춤(C2)**: 결합 AUC 0.789 로 가장 현실적이나 SPEC §4 의
  "상관계수 0.3~0.5" 요건을 위반한다. 평가 감점 위험이 있어 채택하지 않는다.
- **상관 0.7 이상의 강한 대안 변수**: 사실상 target 누수라 분석 가치가 없다.
- **씬파일러를 소득·연령 조건으로 선정**: 씬파일러 여부가 민감속성과 얽혀 ADR-002 의 편향 분석과
  교란된다. 무작위 선정으로 두 축을 분리한다.
- **전통 피처를 통째로 드롭**: 모델이 씬파일러 여부를 자명하게 학습해버려 비교가 무의미해진다.

## 부기: 불균형 처리 기법 — `class_weight` 채택

### 순위 성능 비교 (전체 학습, 18조합 × 20 fold)

| 피처 그룹 | class_weight | SMOTE | 차이 |
|---|---:|---:|---:|
| traditional_only (XGBoost) | **0.8355** | 0.8229 | +0.0126 |
| alternative_only (XGBoost) | 0.8946 | **0.8951** | −0.0005 |
| combined (XGBoost) | 0.9485 | **0.9491** | −0.0006 |
| combined (LightGBM) | 0.9470 | **0.9483** | −0.0013 |

`traditional_only` 에서는 `class_weight` 가 명확히 우세하다(+0.0126).
`combined` 에서는 SMOTE 가 근소 우세하나 **차이가 0.0006 ~ 0.0013 으로 CV 표준편차(±0.0024) 미만**이라
유의한 차이로 볼 수 없다.

F1 은 SMOTE 가 크게 앞선다(combined/XGBoost 기준 0.6274 vs 0.4519). 다만 이는
**승인 임계값 0.30 에서의 점수 분포 차이**이며 순위 성능(AUC·KS)의 차이가 아니다.
SMOTE 로 학습한 모델은 예측 확률이 더 높은 쪽으로 이동해 고정 임계값에서 유리하게 보인다.

### 최종 채택: `class_weight='balanced'`

성능이 사실상 동등하므로 **설명가능성**을 기준으로 고른다.

SMOTE 는 원본에 존재하지 않는 **합성 샘플**로 학습한다. 이 모델의 SHAP 기여도를
고객에게 대출 거절 사유로 제시하면, 실재하지 않는 데이터에서 학습된 관계를 근거로
불이익 처분을 설명하는 셈이 된다. **신용정보법 제36조의2**(자동화평가 결과에 대한 설명 및 이의제기)의
설명 의무와 SPEC §7 의 금융 규제 대응 요건을 고려해 `class_weight='balanced'` 를 채택한다.

SMOTE 는 SPEC §2 의 "불균형 처리 기법 2개 이상 비교" 요건을 위해 비교 실험으로 계속 학습·기록한다.
