# 9. 검증 과정에서 발견하고 수정한 오류

이 장은 결과가 아니라 **과정**의 기록이다. 앞 장의 수치가 믿을 만하다고 주장하려면, 그 수치가
틀렸던 순간과 그것을 어떻게 잡았는지를 함께 보여야 한다.

각 항목은 증상 → 원인 → 조치 → 재발 방지 순으로 적는다. 재발 방지는 **자동 테스트로 강제되는 것**과
**사람이 지켜야 하는 절차**를 구분해 적었다. 이 구분을 하다가, 재발 방지 테스트가 있다고 생각했던
두 건에 실제로는 테스트가 없다는 것을 발견해 이 장을 쓰는 중에 추가했다(9.4절).

### #10 의 재정정

16세션에 SMOTE 비교표를 최종 데이터로 고치면서 결론을 "class_weight 가 **9쌍 중 7쌍에서 우세하거나
동등**"으로 적었다. 17세션에 반올림 전 값으로 다시 세어 보니 다음과 같았다.

| 판정 | 쌍 수 | 내역 |
|---|---:|---|
| class_weight 우세 | 7 | traditional 3쌍, alternative XGB·LGBM, combined XGB·LogReg |
| 사실상 동등 | 1 | alternative LogReg (차이 −0.00005) |
| SMOTE 우세 | 1 | combined LightGBM (−0.0013, CV SD ±0.0025 미만) |

"우세하거나 동등"은 **8쌍**이 맞다. 같은 문단의 "SMOTE 가 이긴 경우는 한 쌍뿐"과도 모순이었다.
결론의 방향(`class_weight` 채택)은 바뀌지 않지만, 오류를 고친 문장에 새 오류가 들어간 사례다.

### #11 의 영향: 결론은 같아도 사실이 바뀌었다

| 항목 | 기록돼 있던 값 (`bias_ratio=0.1`) | 최종 값 (`bias_ratio=0.3`) |
|---|---|---|
| SHAP 1위 `telecom_payment_rate` | 1.3460 | **1.0272** |
| SHAP **2위** | `RevolvingUtilization` 0.7769 | **`spending_consistency` 0.8200** |
| 1위 / 2위 배율 | 1.7배 | **1.25배** |
| 대안 / 전통 피처당 평균 | 0.6563 / 0.2011 (3.3배) | 0.6374 / 0.2010 (3.2배) |
| ADR-012 Tukey XGB vs LGBM | mean_diff +0.0009, p_adj 0.6137 | +0.0008, **0.6468** |
| ADR-012 학습 시간 근거 | XGB 18.3초 vs LGBM 16.8초 | XGB **19.0초** vs LGBM **22.3초** |

"대안 피처가 1위다", "두 알고리즘은 유의차가 없다"는 결론은 그대로다. 그러나 **2위 피처가 무엇인지**,
**LightGBM 이 더 빠른지**는 사실이 뒤집혔다. 옛 값은 PROGRESS·목차를 거쳐 6장 작성 계획에까지 옮겨져 있었고, 6장을 쓰면서
`global_importance.csv` 와 대조하다가 드러났다.

## 9.2 반복된 유형 ①: stale 수치 — 5건, 모두 같은 뿌리

| 사례 | 발견 | 남아 있던 곳 | 발견 경위 |
|---|---|---|---|
| ① `/anova` 결과 (#4) | 12세션 | API 사전 계산 JSON | `/anova` 엔드포인트 구현 중 발견 |
| ② 4장 인용 수치 3건 | 15세션 | 리포트 초안 (v1/v2 비교표 조합 혼용, 측정 시점 미표기, uplift 표 이전 실행 값) | 장 작성 후 교차검증 |
| ③ ADR-001 SMOTE 표 (#10) | 16세션 | ADR 부기 | 5장 작성 중 교차검증 |
| ④ SHAP 전역 중요도 (#11) | 17세션 | `PROGRESS.md`, 리포트 목차 | 6장 작성 중 CSV 대조 |
| ⑤ ADR-012 Tukey · 학습 시간 (#11) | 17세션 | ADR 본문, `simulator_diagnosis.md` | 옛 수치 문자열로 저장소 전체 검색 |

**다섯 건 모두 11세션의 데이터 재생성(ADR-002 v3, `bias_ratio` 0.1 → 0.3) 이전 값이다.**
재생성은 산출물 파일(모델, CSV, JSON, 그림)을 전부 새로 만들었다. 그러나 그 전에 산출물에서
사람이 옮겨 적은 **문서 속 수치**는 누구도 다시 만들지 않았다. ①만 산출물 자체가 낡은 경우이고,
나머지 넷은 산출물은 최신인데 문서가 낡은 경우다.

이 유형이 위험한 이유는 **그럴듯하기 때문이다.** 옛 값과 새 값은 자릿수가 같고 대부분 결론의
방향도 같다. 그래서 읽는 사람이 이상함을 느끼지 못한다. 하지만 ③은 결론을 뒤집었고
("SMOTE 근소 우세" → "class_weight 7쌍 우세"), ④는 사실(2위 피처)을 바꿨다.

### 대책과 그 한계

| 대책 | 적용 | 효과 |
|---|---|---|
| 장마다 인용 수치를 산출물에서 다시 계산해 대조 | 15세션부터 | ②~⑤ 를 전부 이 절차로 잡았다 |
| 표마다 측정 조건 각주 (`bias_ratio`, 표본, 임계값) | 15세션부터 | 옛 수치가 섞였을 때 **조건이 달라 보여** 눈에 띈다 |
| 옛 수치 문자열로 저장소 전체 검색 | 17세션 | ⑤ 를 찾았다. 한 곳에서 stale 을 발견하면 같은 값이 다른 곳에도 있다 |
| 문서 수치를 산출물에서 자동 생성 (템플릿화) | **미적용** | 근본 대책이지만 적용하지 않았다(10장) |

## 9.3 반복된 유형 ②: 한 곳만 고친 수정

| 사례 | 고친 곳 | 남은 곳 | 드러나기까지 |
|---|---|---|---|
| #3 → #12 '기록 없음' 분기 | API 경로 (`null` 입력) | 배치 경로 (센티넬 + 플래그) | 4세션 |
| #9 ADR-004 v2 | 코드 · 설정 | ADR 문서 | 4세션 |
| #10 재정정 | 비교표 수치 | 결론 문장의 셈 | 1세션 |

세 사례 모두 **같은 정보가 두 경로 이상으로 흐르는데 한 경로만 고쳤다.** '기록 없음'이라는 정보는
API 에서는 `None` 으로, 배치에서는 `−1` 과 플래그로 들어온다. ADR-004 의 목적함수라는 정보는 설정 파일과
문서 두 곳에 산다. 수정한 곳에서 테스트가 통과하면 끝났다고 느끼기 쉽다.

#9 는 특히 교훈이 크다. 편집 도구가 성공 메시지를 냈지만 실제로는 아무것도 바꾸지 않았다.
이후로는 텍스트 편집 뒤 치환 건수를 `assert` 로 확인한다. 17세션에도 ADR-012 편집 1건이
표 구분선(`|---|---:|`) 불일치로 실패했는데, 이번에는 도구가 실패를 보고해 즉시 다시 적용했다.
조용히 실패했다면 사례 ⑤ 가 수정된 척 남았을 것이다.

## 9.4 재발 방지 장치의 실태

| 재발 방지 | 건수 | 해당 |
|---|---:|---|
| 자동 테스트 | 6 | #1, #2, #3, #5, #7, #12 |
| 수동 절차 · 문서 | 6 | #4, #6, #8, #9, #10, #11 |

자동 테스트 6건 중 **#2 와 #3 은 이 장을 쓰기 전까지 테스트가 없었다.** 목차 초안에는
"각 오류는 재발 방지 테스트를 함께 추가했다"라고 적어 두었는데, 테스트 이름을 표에 채우려고
확인해 보니 #3 은 `/predict` 경로만 검사하고 있었고(`/explain` 은 검사하지 않음), #2 는 참조 평균
테스트가 센티넬 제외를 확인하지 않았다. 두 테스트를 추가해 pytest 는 166 → 169건이 됐다
(#12 회귀 테스트 포함).

수동 6건은 대부분 **문서와 산출물의 정합성** 문제다. 코드의 오류는 테스트로 막을 수 있었지만,
"문서에 적힌 숫자가 최신인가"는 테스트가 검사하지 않는다. 이 프로젝트에서 가장 많이 반복된
오류가 바로 그 영역에 있다.

## 이 장의 결론

1. **12건의 오류 중 자동 테스트로 재발을 막는 것은 6건이다.** 그중 2건은 이 장을 쓰며 테스트가
   없다는 것을 발견해 추가했다. 나머지 6건은 문서·산출물 정합성 문제라 사람의 절차에 의존한다.
2. **가장 많이 반복된 유형은 stale 수치(5건)이며, 모두 11세션 재생성 이전 값이다.** 산출물을
   재생성하면 산출물에서 옮겨 적은 문서 수치를 전수 대조해야 한다. 결론이 같아도 사실이 바뀔 수
   있다(SHAP 2위 피처, LightGBM 학습 속도).
3. **수정은 한 경로에만 적용되기 쉽다.** '기록 없음' 분기는 API 에서 고친 뒤 배치 경로에서 4세션
   동안 남았다. 같은 정보가 흐르는 다른 경로를 함께 점검하고, 편집은 결과를 확인해야 한다.
